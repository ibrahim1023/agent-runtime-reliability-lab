# Approval: a proposal is not an executed action

## What to inspect

Open `results/historical/approval/approve.json`, `reject.json`, and `edit.json`. Each records three phases in distinct processes: initial request, restart without a decision, and simulated reviewer decision.

In initial and restore phases, compare the complete interrupt request and conversation messages. They are unchanged, both ledger snapshots are empty, and the pending node is the approval middleware. The journal has worker-start entries but no tool-body entry before the reviewer decision.

## Why a tool message is not proof of execution

The rejection case contains an error-status tool message generated by middleware. The journal contains no tool-entry event and the SQL receipt export is empty. A tool message can tell the model about a denial without executing the requested action.

In the edit case, conversation history retains the original `original-proposal` request. The simulated reviewer supplied `reviewer-approved` before execution. The actual tool-entry journal and committed receipt contain only the replacement. The returned tool-call ID matches the original proposal, and the response notice explains the replacement. Read the executed arguments and artifact rather than inferring execution from the model's original request.

## What is checked

The offline verifier checks file identity, three process identities, unchanged pending review, empty pre-decision ledgers, journal ordering, simulated decision source, strict replacement contents, receipt consistency, and tool-result identity. Negative tests use temporary altered copies, including recomputed file hashes, to test claim consistency rather than hashing alone. A rejection with a tool-body entry, a changed interrupt, or an edit committing the original is rejected.

This validates stored observations; it does not recreate LangGraph, authenticate a reviewer, inspect original checkpoints, or prove a malicious journal could not be fabricated. Original source hashes are provenance pointers, not cryptographic signatures of execution.

## Historical evaluator correction

The original reviewer-edit lab initially rejected display text containing a nonbreaking hyphen (U+2011). Its display comparison was corrected without rerunning the model. Actual tool arguments and ledger contents remained strictly checked. This export retains the displayed final response and does not normalize the executed payload or report the correction as a new model trial.

## Still untested together

Pending approval and post-commit tool replay were demonstrated separately. The approval → receiver commit → crash → resume intersection remains a new experiment to implement. These exports do not establish how approval behaves at that crash boundary.
